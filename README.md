# OANDA demo bot

Standalone Node 22+ service. No packages are required. Run `npm test`, then `npm start`.

Set `OANDA_DEMO_TOKEN` privately in Render Environment settings, and Save and deploy. Do not paste it into chat, GitHub, a URL, or the public page. The app selects the account only when exactly one demo account is available; otherwise set `OANDA_ACCOUNT_ID` to the intended v20 demo account. MT4-linked accounts are rejected. Set `BOT_ENABLED=false` and deploy to stop new entries. This does not cancel broker-held orders or close positions: manage those in OANDA.

The broker origin is hardcoded to `https://api-fxpractice.oanda.com`. There is no live mode or public configuration/order endpoint. The status page is public and intentionally excludes account IDs, tokens, balances, prices and detailed trades.

The service polls completed M1 EUR/USD candles every 30 seconds. It implements previous UTC hour/four-hour/day levels, a sweep, five-bar structure reversal, simultaneous three-candle fair value gap, midpoint limit, swing stop, and nearest opposing prior level. It does not reproduce discretionary order blocks, inverse gaps or Fibonacci extensions. Entries occur weekdays 08:00–11:00 London time, with DST applied. Holidays are not separately modeled. Missing-minute gaps reset signals.

Each entry is fixed at ONE EUR unit. This is a deliberately tiny functional demo, not a risk-scaled money-making bot. At most two accepted limit orders per London day; cancellations still count. Any pending order or open trade in the chosen account blocks another entry. Use a dedicated demo account and a single service instance. Limit orders expire ten minutes after the confirmation candle closes. Stops and targets are attached through OANDA. Spread must be no more than 20% of stop distance and (reward-spread)/(risk+spread) at least 1.5. These controls do not establish profitability or guarantee fills or loss limits.

On startup the bot waits 90 seconds and ignores signals already present during that period. It never catches up missed entries. History is read from OANDA to detect duplicate signal IDs and count orders across restarts. A POST is never retried; an ambiguous submission pauses this process for manual broker review. Do not restart blindly following that message. The process does not persist a cross-instance lock; do not scale or run another copy. A 90-second startup delay reduces overlap during ordinary deployment but is not a distributed lock.

Free Render services sleep after 15 minutes without incoming traffic. Outgoing broker polling does not make them continuously available. The service cannot monitor continuously on free hosting when the status page is closed. Broker-held orders, stops and targets remain at OANDA while the app sleeps. Paid always-on hosting requires separate cost approval.

Validation: tests use synthetic candles and mocked HTTP, including a complete submission path. An authenticated broker connection and actual demo fill MUST be verified after private token setup. No performance or profitability claim is made. This is not the original replay engine with realistic-market performance validation.

Version 1.1: displays actual pending/open counts and daily order totals; restores submission history after restart; describes each signal stage and closed entry sessions; caches completed candles and timezone formatters; refreshes broker state before submission; blocks non-finite margin data; stops new submissions during shutdown. The deployed service uses the approved paid always-on plan. The generic free-plan limitation above applies only if it is downgraded. All validation remains functional, not proof of profitability.

Version 1.2 adds read-only research in a worker thread, isolated from the execution loop. It downloads 90 calendar days of complete M1 bid/ask/mid EUR/USD candles from OANDA, partitions chronologically 60/20/20, runs fixed-rule candle simulations with actual spreads and a one-pip-per-side slippage stress scenario, and trains an L2 logistic directional model for a five-minute horizon using development data only. Labels that cross a split boundary are excluded. The validation/test splits are scored against the training-frequency forecast using Brier score. Overlapping labels mean rows are not independent observations. This model NEVER controls trades, even if its Brier score improves. No parameter search or automated strategy selection occurs. Worker results at /api/research are aggregate research outputs; no tokens, account IDs, balances or detailed private trades are included. History is inspected separately for actual bot order acceptance, fills and closures. No fill is claimed unless matching broker transactions exist. Research reruns after a restart; it is not a persistent audit database. Runtime failure does not change strategy parameters or enable real-money trading.

Version 1.3 redesign: historical coverage expands to 180 calendar days. Three fixed, named alternatives are compared (20/60-minute trend breakouts and a 20-minute range-reversion rule). All use completed five-minute checks on one-minute source candles, ATR-based stops, spread-aware order checks, one-EUR-unit size and the existing two-order/day limit. Development/validation gates require at least 20/10 filled trades, positive stress-case P/L in both periods and validation profit factor >=1.1. One candidate is frozen on validation stress-case mean P/L; only that candidate opens the final holdout. Promotion also requires >=10 holdout trades, >=50 total trades, holdout profit factor >=1.1, positive stressed holdout P/L, and a positive lower bound from 500 circular three-day block-bootstrap resamples of holdout daily P/L. These are screening criteria, not guarantees. Final dates overlap earlier original-strategy research, so they are explicitly not represented as pristine unseen data. Future forward-demo confirmation remains necessary. No new demo orders are allowed during validation or if every candidate fails. Research or worker failure leaves new entries paused while existing broker stops and monitoring remain in place. No live-money mode or forecast-controlled entries is added. No hosting upgrade is introduced.

Execution correction: passive buy limits are checked against the current ASK and sell limits against the current BID. The prior exit-side comparison could incorrectly reject valid inside-spread limits. The stop, spread and net reward/risk checks remain in place. Research reports signal counts and named order rejection reasons, so zero trades cannot silently masquerade as a performance finding. Median spread and M1 range diagnostics accompany each study.

Version 1.4: owner-authorized demo forward testing is independent of historical promotion. DEMO_FORWARD_STRATEGY must name one of the three fixed candidates; an unknown ID fails closed. DEMO_EXTENDED_SESSION=true permits weekday forex hours rather than only 08:00–11:00 London. Existing historical results remain explicitly unvalidated and are not applicable evidence for the expanded schedule. Trade size stays one EUR unit; at most two accepted strategy orders per London day, one outstanding order/trade, fixed broker stops/targets and expiry, spread and reward/risk checks, stale-price protection and no order-write retries remain active. A failed historical study cannot silently disable an explicitly requested demo forward test. Real-money hosting endpoints remain absent.

DEMO_EXECUTION_CHECK_ID authorizes one labelled technical demo round trip: a one-unit EUR/USD FOK market entry with attached stop/target, followed immediately by closing only the returned owned trade ID. Client order/trade IDs are checked on restart, so a previous accepted technical order is never resent. This uses the same hardcoded practice host. A PUT is allowed only on the specific numeric trade-close endpoint, and is never retried. Existing unrelated orders/trades cause the test to skip. An uncertain result blocks new entries for review. This technical fill is labelled separately from strategy performance and never establishes profitability.

The one-off technical market entry counts toward the same two-order daily cap; its automatic close does not count as another entry. The historical comparison retains its original three-hour schedule. Expanded-hour results must be assessed prospectively, separately from that earlier study.
